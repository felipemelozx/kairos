# Kairos MVP – Product Requirements Document (PRD)

## 1. Product Vision

**Kairos** is a calendar-first time productivity system where **only executed time counts as progress**.

The product helps a single user plan their time, track what they commit to do, and measure real execution — all in one place.

Kairos combines:

- Calendar-based time planning (Google Calendar–like, with recurring commitments)
- Inline checklists inside each time block (what to do within that time)
- Real execution tracking via a **timer** (the single source of truth)

The differentiator is the **Review** view: planned vs executed, per day and per project.

---

## 2. Problem Statement

Most productivity tools either:

- Focus on **planning** (calendars) without validating execution, or
- Focus on **tasks** without accounting for real time spent.

As a result, users confuse **planned time** with **actual progress**.

Kairos solves this by clearly separating:

- **Intention** (time blocks and their checklists)
- **Reality** (execution logs produced by the timer)

Only what is executed and logged counts as progress. A time block that passes without execution produces zero progress.

---

## 3. Target User

**Primary user:** the maintainer (and possibly a small circle of people).

The product is built for personal, single-user use. There is **no multi-tenancy, no organizations, no roles, and no team collaboration** in the MVP.

User characteristics:

- Already uses calendars and task tools
- Feels friction switching between tools
- Cares about time awareness and consistency
- Works in multiple life/work contexts (study, work, clients)

---

## 4. Core Principles (Non‑Negotiable)

1. **Time blocks are intentions, not execution**
2. **Execution logs (timer sessions) are the only source of truth**
3. **A time block that passes without execution produces no progress**
4. **Projects are life/work contexts, not folders**
5. **Time is the central axis of the system**
6. **History is immutable** — editing a recurring series never rewrites the past
7. **Every resource is scoped to its owner user** — no user can access another user's data

## 5. Core Entities (MVP)

### 5.1 User

The single account owner. All data belongs to a `userId`.

- id
- email (unique)
- name
- avatarUrl
- active
- createdAt

Authentication: OAuth2 + Google, with JWT (access + refresh tokens).

### 5.2 Project

Represents a long‑term context or objective.

Examples:

- Study English
- University – Algorithms
- Client João

Fields:

- id
- userId
- name
- description
- color
- status (active / archived)
- createdAt
- deletedAt (soft delete)

Notes:

- Clients are represented as projects
- No separate CRM entity exists in MVP

### 5.3 Time Block

Represents reserved time in the agenda. **Every occurrence is a materialized row in the database.**

Fields:

- id
- userId
- title
- startDateTime
- endDateTime
- projectId (optional)
- seriesId (nullable — set when this block was generated by a recurring series)
- isOverride (whether this occurrence was individually edited and detached from the series rule)
- createdAt
- deletedAt (soft delete)

Rules:

- Time blocks do not generate progress
- A time block may contain multiple checklist items
- A block that passes without execution produces no progress
- `endDateTime` must be > `startDateTime`

### 5.4 Time Block Series (Recurrence)

Represents a repeating commitment (e.g., "English every Mon/Tue").

Fields:

- id
- userId
- title
- projectId (optional)
- recurrence pattern (see 5.5)
- startDate
- endDate (optional — if absent, the series runs indefinitely and is rolled forward)
- createdAt
- deletedAt (soft delete)

Rules:

- A series **materializes occurrences** into `time_blocks` up to a horizon (12 months ahead)
- A **roll-forward job** (daily/weekly) creates new occurrences as time passes
- **Series split on forward edit**: changing a series rule from date X onwards closes the old series the day before X and creates a new series starting at X. History is never rewritten.
- **Per-occurrence override**: editing/moving a single occurrence turns that block into a standalone block (`isOverride = true`), leaving the rest of the series untouched.

### 5.5 Recurrence Pattern (MVP scope)

The MVP supports **simple daily/weekly patterns only** — no full RRULE engine:

- **Daily** (every day)
- **Daily with interval** (e.g., every 2 days)
- **Weekly with chosen weekdays** (e.g., Mon & Wed; only Mon)
- **Single one-off event** (no series; e.g., a job interview tomorrow)
- All patterns have a fixed time of day and duration
- Optional end date ("ends on 30/Oct") or indefinite ("forever")

Explicitly out of scope: monthly-on-day-N, "last Friday of month", complex RRULE exceptions.

### 5.6 Checklist Item

Represents what to do **within** a time block.

Fields:

- id
- timeBlockId
- title
- done (boolean)
- createdAt

Rules:

- Checklist items are **not tasks**: they have no status workflow, no own time log, no project association
- Checking an item marks it done — nothing more
- Checklist items **do not survive** across occurrences of a series; each occurrence starts with an empty checklist
- The Kanban board is an **aggregating view** over these checklist items, not a separate entity

### 5.7 Work Session (Execution Log)

Represents real work performed, produced by the **timer**.

Fields:

- id
- userId
- startedAt (Instant — real clock)
- endedAt (Instant — real clock)
- durationMinutes (derived)
- projectId
- timeBlockId (nullable)
- notes (optional)
- createdAt

Rules:

- Only work sessions generate metrics and progress
- Work sessions are **immutable** once created
- A work session is created when the timer stops
- The timer **stops automatically at the end of the time block** — no forgotten timers
- When the block ends and work continues, the app offers: "register 12h–12h40 as extra time in the same project?" → a **one-tap orphan log** (no timeBlockId, still tied to projectId)
- Work sessions use **physical deletion** (not soft delete)

---

## 6. Timer Behavior (Core Flow)

1. User opens a time block and presses **Start**
2. The app runs the timer (startedAt recorded)
3. The timer **stops automatically** at `endDateTime`
4. On stop, the app creates a Work Session with `startedAt`/`endedAt`
5. If work continues past the block end, the app offers to register the extra time as an orphan log on the same project
6. Work sessions are immutable; block remains closed

Edge cases (resolved):

- **Forgotten timer**: impossible — the timer always stops at the block end
- **Overtime**: captured via the optional orphan log (no time is silently lost or silently inflated)
- **Multiple blocks per day**: each block runs its own independent timer → separate work sessions

## 7. User Flows (MVP)

### 7.1 Planning Flow

1. User creates a project
2. User creates a time block or a recurring series in the calendar
3. Optionally, user adds checklist items inside the block
4. The calendar materializes occurrences (for series) automatically

### 7.2 Execution Flow

1. User opens a time block and presses Start
2. The timer records the real session
3. At block end the app creates the work session automatically
4. Overtime is offered as an orphan log
5. The user checks off checklist items as they go

### 7.3 Review Flow

1. User views planned vs executed time per day and per project
2. User checks consistency and project progress
3. User compares intention vs reality honestly

## 10. Recurrence Rules (MVP)

1. Series materialize occurrences as rows in `time_blocks`, up to a **12-month horizon**
2. A **roll-forward job** generates new occurrences over time (series with no end date)
3. **Forward edit (series split):** changing the rule from date X → old series ends the day before X; new series starts at X. History untouched.
4. **Single occurrence edit (override):** the edited block becomes `isOverride = true` and is independent of the series; remaining occurrences stay generated by the rule.
5. **Deleting a series** soft-deletes its future occurrences; past occurrences remain (history is immutable).

## 11. Non‑Goals (Explicitly Out of Scope for MVP)

- Multi-tenancy / organizations / roles / team collaboration
- Standalone tasks with status workflow (tasks are checklists inside blocks)
- Kanban as an independent entity (it's a view over checklists)
- "Task can only be done with execution log" rule (execution is per block, not per checklist)
- AI suggestions or automation
- Automatic task scheduling
- Goals or quotas
- Dedicated CRM module
- Mobile optimization
- Full RRULE recurrence engine (monthly-on-day-N, complex exceptions)
- Redis caching / blue-green deploy / 99.9% uptime SLA

## 14. Technical Architecture

### 14.1 Architectural Style

Kairos backend follows a **Layered Architecture** (controller → service → repository → entity), as defined in `docs/architecture/backend-architecture.md`.

**Key Architectural Principles:**

- **Dependency direction**: Dependencies flow downward only (`controller → service → repository → entity`)
- **Business logic in services**: All business rules live in the service layer
- **Transactions**: `@Transactional` lives on service methods only
- **DTOs at the edges**: Request/response DTOs are used only at the HTTP boundary

### 14.2 Technology Stack

| Component | Technology | Version |
|-----------|------------|---------|
| **Backend Framework** | Spring Boot | 4.0.1 |
| **Language** | Java | 21 |
| **Database** | PostgreSQL | 16.8 |
| **Migrations** | Flyway | - |
| **Security** | Spring Security + OAuth2 + JWT | - |
| **Testing** | JUnit 5, Testcontainers, Mockito | - |
| **Build Tool** | Maven | - |
| **Frontend** | Next.js 14 (React 18) + Zustand + date-fns | - |
| **Deployment** | Docker, Docker Compose, GitHub Actions | - |
| **Infrastructure** | Single VPS (self-hosted) | - |

### 14.3 Deployment Model

- **Target**: self-hosted on a single VPS with Docker Compose (PostgreSQL + backend + frontend)
- **Development**: same Docker Compose stack locally
- The project is **built as if it lives on a VPS**; free-tier cloud hosting (Vercel/Render/Railway/Neon) is an optional deployment variant that **never dictates architecture**
- **No Redis, no blue-green, no multi-instance** in the MVP

## 15. Data Model

### 15.1 Multi-Tenancy → Owner Scoping

All data is scoped to a **single `userId`**. There are no organizations.

- Every table carries `user_id`
- Every query filters by the authenticated user

### 15.2 Entities

#### User
```
- id: UUID (PK)
- email: String (unique)
- name: String
- avatarUrl: String (optional)
- active: Boolean
- createdAt: Instant
```

#### Project
```
- id: UUID (PK)
- userId: UUID → User.id
- name: String
- description: String
- color: String (hex #RRGGBB)
- status: ACTIVE / ARCHIVED
- createdAt: Instant
- deletedAt: Instant (soft delete)
```

#### TimeBlock
```
- id: UUID (PK)
- userId: UUID → User.id
- title: String
- startDateTime: Timestamp
- endDateTime: Timestamp
- projectId: UUID → Project.id (optional)
- seriesId: UUID → TimeBlockSeries.id (optional)
- isOverride: Boolean (default false)
- createdAt: Instant
- deletedAt: Instant (soft delete)
```

#### TimeBlockSeries
```
- id: UUID (PK)
- userId: UUID → User.id
- title: String
- projectId: UUID → Project.id (optional)
- startDate: Date
- endDate: Date (optional)
- pattern: JSONB  (daily / daily-interval / weekly-weekdays, time, duration)
- createdAt: Instant
- deletedAt: Instant (soft delete)
```

#### ChecklistItem
```
- id: UUID (PK)
- timeBlockId: UUID → TimeBlock.id
- title: String
- done: Boolean (default false)
- createdAt: Instant
```

#### WorkSession
```
- id: UUID (PK)
- userId: UUID → User.id
- startedAt: Timestamp
- endedAt: Timestamp
- durationMinutes: Integer (derived)
- projectId: UUID → Project.id
- timeBlockId: UUID → TimeBlock.id (optional)
- notes: String
- createdAt: Instant
```

**Note**: WorkSessions use **physical deletion** (not soft delete) — they are immutable records.

### 15.3 Data Integrity Rules

1. **Time Range**: `endDateTime` must be > `startDateTime` for TimeBlocks
2. **Session Range**: `endedAt` must be > `startedAt` for WorkSessions
3. **Series Split**: splitting a series must never modify existing occurrences created before the split date
4. **Override**: an overridden occurrence keeps its id but is detached from series regeneration
5. **Owner Scoping**: all data access must validate the resource belongs to the authenticated user

### 15.4 Database Indexes

```sql
-- Only index non-deleted records
CREATE INDEX idx_projects_user_active ON projects(user_id, status)
WHERE deleted_at IS NULL;

-- Calendar queries
CREATE INDEX idx_timeblocks_user_range ON time_blocks(user_id, start_datetime, end_datetime)
WHERE deleted_at IS NULL;

-- Metrics queries
CREATE INDEX idx_sessions_user_date ON work_sessions(user_id, started_at);

-- Checklist aggregation
CREATE INDEX idx_checklist_block ON checklist_items(time_block_id);
```

## 16. Security

### 16.1 Authentication

OAuth2 + Google Login with JWT (access token 15 min, refresh token 7 days). Standard flow: frontend redirects to Google → backend creates/updates user → returns tokens.

### 16.2 Authorization (Owner Scoping)

**Model: service-layer discipline, enforced by structure and tests.**

1. **Repository convention (compile-time)**: repositories expose scoped methods only — e.g., `findByIdAndUserId(id, userId)`. Unsafe unscoped methods (`findById`) are **not exposed**. Forgetting the user filter becomes a compile error, not a runtime bug.

2. **Authorization tests (CI)**: every GET/PATCH/DELETE endpoint has a test asserting "user B cannot access user A's resource". Forgetting to write the test fails CI.

3. All requests resolve the user from the JWT; services pass the authenticated `userId` into every repository call.

### 16.3 Input Validation

Two-level validation:

1. **DTO Level** (Bean Validation): structural rules — `@NotNull`, `@NotBlank`, `@Size`, `@Pattern`
2. **Service Level** (Business Rules): cross-field validation, invariants, owner-scoping validation

## 17. Non-Functional Requirements

### 17.1 Performance

- API response time < 200ms (p95) for regular queries — indexed queries on single-user data are trivially fast
- No caching layer in the MVP (single user; data volume is small)

### 17.2 Availability

- Single-VPS deployment; uptime driven by standard Docker Compose restarts
- Health checks via `/actuator/health`
- Daily PostgreSQL backups

### 17.3 Observability

- Structured JSON logs (SLF4J + MDC with `requestId`, `userId`)
- Micrometer + Prometheus endpoint
- Actuator health endpoints

### 17.4 Quality Gates (Mandatory)

Because the codebase is generated with AI assistance, quality gates are **non-negotiable**:

- Unit tests (services, validation) — mandatory for every feature
- Integration tests (persistence, controllers) via Testcontainers
- Authorization tests per endpoint (owner scoping)
- Coverage target: 80%+ (JaCoCo), never reduced by a change
- Zero SonarQube/ESLint blocking warnings
- Lint + typecheck for the frontend (`npm run lint`, `npm run type-check`)
